## 2. How it is put together

**Frontend** — React 19 + TypeScript, built by Vite, served as a PWA. Tailwind CSS v4.

**Backend** — Supabase (project ref `pwkpjgdmjvxjrbufmdyv`): Postgres with row-level security, passwordless auth, and two Edge Functions.

**Hosting** — Cloudflare Pages, project `busybeegrocer`. DNS is on Cloudflare nameservers; the domain is still *registered* at GoDaddy (renewals happen there).

**Other services** — Resend sends sign-in emails via a Supabase auth hook. Cloudflare Turnstile guards sign-in. Sentry collects crashes.

### The `/app` split

The landing page occupies `/`, the app lives under `/app/`. In the built output:

```
dist/
  index.html          landing page          (from site/)
  404.html            real 404 page         (from site/)
  _redirects          routing rules         (from site/)
  _headers            cache rules           (from site/)
  app-shell.html      copy of the app's index.html — SPA target
  app/                the built app
    404.html          copy of index.html — fallback for unlisted routes
```

Nothing in the app hardcodes `/app`. Every path comes from `import.meta.env.BASE_URL`, set by `base` in `app/vite.config.ts`. Changing that one line moves the whole app — router, assets, manifest, magic-link redirect and the share QR all follow.

## 3. Making a change

```bash
cd C:\Users\rexma\ClaudeOS\Shopping-List\app
npm install          # first time only
npm run dev          # http://localhost:5173
```

Before committing:

```bash
npm run build        # typechecks, then builds
npm test             # unit tests
npm run lint
```

To check the deployed site rather than the dev server — routing, the landing page, cache headers — build the real thing and serve it the way Cloudflare will:

```bash
npm run build
npm run assemble                     # same script CI runs
npx wrangler@4 pages dev ../dist     # http://127.0.0.1:8788
```

This is the only way to test routing. `npm run dev` serves the app at `/`, not `/app/`, and knows nothing about `_redirects`.

Then:

```bash
cd ..
git pull --rebase origin main      # ALWAYS — see trap 3
git add <files>
git commit -m "fix: what changed and why"
git push origin main
```

Pushing to `main` deploys. Nothing else is needed.

### Commit messages decide the version number

| Prefix | Result |
| --- | --- |
| `fix:` | patch — 2.0.2 → 2.0.3 |
| `feat:` | minor — 2.0.2 → 2.1.0 |
| `feat!:` with a `BREAKING CHANGE:` footer | major — 2.0.2 → 3.0.0 |
| `docs:` `chore:` `build:` `refactor:` | **no release**, but still deploys |

Anything not matching produces no version bump. The version shows on the Settings screen, so a wrong prefix means the app misreports itself.

The subject line is also **published**: it becomes a row on the Release History page
(`/app/releases`, linked under the version in Settings), with `fix:`/`feat:` deciding
whether it reads as Fix or Feature. Write it for the person reading it there.

## 4. Database changes

Migrations live in `supabase/migrations/`, named `<timestamp>_<snake_case_name>.sql`.

They are applied through the **Supabase MCP connector from a Claude session**, not the Supabase CLI. The folder is a mirror of what has been applied, kept in step by hand.

⚠️ **The CLI is not set up, and `supabase db push` would try to re-create the whole schema.** If you ever adopt it, `supabase link` first and check the recorded migration history matches these filenames before pushing anything.

To change the schema: ask Claude to write the migration, review the SQL, then have it apply and verify. Always ask it to test the result in a transaction it rolls back.

**Edge Functions** are in `supabase/functions/`:
- `send-email` — the Supabase auth hook that routes sign-in emails through Resend
- `delete-account` — lets someone delete their own account (a browser cannot do this itself)

Deployed through the Supabase connector, not from the repo.

## 5. How a deploy works

`.github/workflows/deploy.yml`, on every push to `main`:

1. `npm ci`, then `npm test` — a failing test stops the deploy
2. `semantic-release` reads commits, bumps the version, commits it back with `[skip ci]`
3. `npm run build` — Vite writes to `dist/app`
4. Copies `site/` over `dist/`, and makes `app-shell.html` and `app/404.html`
5. Sanity-checks the assembled directory
6. `wrangler pages deploy dist` — a direct upload

The version bump happens **before** the build, so the app reports the release it actually is. This is why Cloudflare is *not* connected to Git: a Git-triggered build would build the pre-bump commit and then skip the release commit because of its `[skip ci]` marker.

`.github/workflows/redirect-shell.yml` is separate and manual. It publishes `redirect-shell/` to the old GitHub Pages address. It has been run. Only run it again if you change that page.

### Secrets

| Secret | What it is |

## 6. Traps

These are the things that have already gone wrong, or would.

**1. The routing rules are generated — don't hand-edit them.**
`app/scripts/assemble.ts` reads the routes out of `App.tsx` and writes the rules into `dist/_redirects`. Add a `<Route>` and its rule appears on the next build. `site/_redirects` holds only the explanatory header. This used to be a hand-maintained list, and a forgotten line meant a route that worked but returned the wrong status.

**2. Never write `/app/*` as a catch-all in `_redirects`.**
Cloudflare evaluates redirects *before* static files, so a catch-all serves the HTML shell for every script, the stylesheet, the manifest and the service worker, and the app never boots. Rewriting to `/app/index.html` instead is silently discarded as an infinite loop. The generator refuses to emit either, and CI rejects a hand-added one.

**3. Always `git pull --rebase` before pushing.**
CI pushes its own release commit, so `main` has usually moved since your last push.

**4. Changes reach phones only after the app is closed and reopened.**
The service worker serves the previous build until then. If someone says a fix isn't there, that's almost always why.

**5. Migration filenames must match what the database recorded.**
See section 4.

**6. Leave the old-URL redirect shell published.**
`redirect-shell/sw.js` retires the service worker that installed copies still run. Without it those copies serve a cached app indefinitely and never learn anything moved.

**7. The offline queue depends on `toggle_list_item_checked` being idempotent.**
It no-ops when an item already holds the requested value (migration `20260806175526`). Undo that and replayed offline changes corrupt the lifetime tallies — and now the Frequently Bought ranking, which the same statement maintains.

**8. The Turnstile site key is hardcoded** in `app/src/components/Captcha.tsx`, deliberately. It is public, and an env var that failed to arrive in CI would lock everyone out rather than degrade.

**9. The Frequently Bought half-life is written in two places.**
90 days, in migration `20260815125948` and in `app/src/lib/frequentlyBought.ts`. Postgres can't share a constant with the browser, so it is duplicated. Change one without the other and the stored score and the displayed score stop measuring the same thing. There's a test for the half-life, but nothing can check the two match — only reading both.

## 7. Tests

`npm test` — Node's built-in runner, no extra dependencies. 75 tests over the pure logic:

- `emailTypos` — sign-in address suggestions
- `quantity` — the text-while-editing quantity field, including the backspace case
- `frequentlyBought` — the frequency-plus-recency ranking behind the Frequently
  Bought panel, including the case it exists for (a big tally that stopped losing
  to a smaller one that didn't) and the pre-migration fallback
- `releaseNotes` — the changelog parser behind the Release History page, including a
  check that the real `CHANGELOG.md` still parses and reaches back to 1.0.0
- `offlineQueue` — queueing, superseding, replay, partial failure
- `offlineCache` — cache envelopes and hostile input
- `groupGate` — the routing decision that once sent people to "Create your group" while offline
- `markdown` — the parser that renders `PRIVACY.md`
- `routeRedirects` — the rule generator, including that it refuses to emit `/app/*`

**Not covered:** anything behind the login wall. The UI has been checked by hand in a browser instead. When Claude changes something it cannot reach, it should say so rather than imply it verified it.

## 8. Known limitations

- **Starting a brand-new shopping trip offline** doesn't work — it needs a server-generated session id. Resuming one offline is fine, and the list itself works fully offline.
- **The app never sends invite emails.** It opens your mail app; you press send. The copy-link button is the dependable route. This is deliberate — see the landing page, which explains it to users.
- **Offline conflicts are last-write-wins.** Two people editing the same list offline merge unpredictably.
- **Deep links return a 404 status** for any route missing from `_redirects`, though the app still loads.
- **Free tiers**: Resend 100 emails/day; Supabase pauses a project after ~7 days of no activity.

## 9. Coming back to this in a new Claude session

Claude reads the memory folder automatically at the start of a session, so it will already know the stack, hosting and history. You do not need to explain the project.

**Open a terminal in the project folder and start Claude there:**

```bash
cd C:\Users\rexma\ClaudeOS\Shopping-List
claude
```

Then say what you want, and point it at this file:

> Read MAINTENANCE.md first. I want to <describe the change>.

That one line is enough. It gets the layout, the deploy pipeline and the traps from this document, and the history from memory.

**Worth saying explicitly, because it changes what Claude does:**

- *"Apply and verify the migration"* — if the change touches the database
- *"Don't push until I've reviewed it"* — if you want to see the diff first
- *"Tell me what you couldn't test"* — most UI sits behind the login wall

**If it needs to test signed-in behaviour**, it will ask you to sign in at `http://localhost:5173` while `npm run dev` is running. Sessions expire fairly quickly, so expect to do that again if you come back to it later in a session.

**Files it should not need to touch:** `app/CHANGELOG.md` (generated), `dist/` (build output), `app/.env.local` (your local Supabase keys).
